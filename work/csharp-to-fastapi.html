Moving services from C# to FastAPI

The platform's payment, affiliate and ticketing services were first built in C# on ASP.NET Core. They now run on Python and FastAPI. This note covers how I approach a port like that, using the ticketing service as the example because its history is fully in my hands.

The rule: the outside must not notice

Other services and the frontend depend on a service's routes, status codes, response shapes and events. A port is successful when none of them can tell it happened. So the first commit of the FastAPI ticketing service was titled Initial ticketing-fastapi baseline with parity tests: the contract tests arrived with the code, not after it.

What a contract test pins down

Real examples from that suite:

  • An operations endpoint called without a token returns 401, never data.
  • The outbox statistics endpoint returns exactly total, published, pending and failed.
  • Replaying failed messages respects the limit the caller sends.

None of these tests cares which language produced the answer. That is the point.

Port the events with the endpoints

A service talks through events as much as through HTTP. The first FastAPI commit already contained the event contracts, the outbox table, the publisher and the schema-discovery service. Porting the HTTP side first and the events later would have left a window where the service answered correctly and told nobody.

What I would tell someone starting a port

  • Write the contract tests before the first route.
  • Port the events in the same step as the endpoints.
  • Make the new service report which version is running, so you always know which side of the port you are looking at.
  • Keep the old service until the new one has passed the same tests in production conditions.
