A support ticketing service on FastAPI

The service behind customer support for a multi-product SaaS platform. I own it end to end: all 42 commits in the repository, from April to September 2026, are mine.

Role
Developer and owner of the service
Stack
Python, FastAPI, SQLAlchemy 2, PostgreSQL, Redis, Apache Kafka (aiokafka), pytest
Size
151 automated tests, 91 Python files, a React/Vite portal in front

The problem

A platform with several products needs one place where support happens. A customer must raise a ticket against the right brand, product and plan. Staff need to pick a ticket up, work it to resolution, and sometimes raise one on a customer's behalf. Support staff need access that is narrow, checkable and never accidentally broader than intended.

What it does

  • Customers raise tickets with a product and plan that the service validates, using a brand, product and plan taxonomy mirrored from the platform's product catalogue.
  • Staff pick tickets up, work them to resolved, and can raise a ticket on behalf of a customer.
  • Attachments and a single-customer view for staff.
  • Staff access is gated by an allow-list of registered staff, restricted to the company's email domain.

How it is built

The code is layered: routes call services, services call repositories, repositories own the models. Events leave the service through a transactional outbox: a ticket change and the message announcing it are written through the same database session, and a worker publishes the message to Kafka afterwards. If the broker is down, the message waits in the outbox instead of being lost.

Data owned by other services reaches this one through Kafka consumers that keep local projections, so the service holds its own copy of what it needs. A separate worker handles schema discovery.

Decisions worth explaining

The broker is not a boot dependency

Kafka consumers start in the background, and fetching broker credentials still works when Redis is unavailable. Early commits fixed exactly this: a messaging problem must degrade the projections, not take the API down.

Fail closed, and say nothing extra in production

The interactive API documentation is removed in production and the machine-readable schema is behind a token. Authorisation decisions use the roles a user is acting in right now, not every role they hold; the role audit case study explains why that distinction matters.

You can tell what is running

A service that cannot say which version it is running forces you to guess during an incident. This one carries a source stamp and its logs reach a place you can read them. A commit titled make the running service observable added both.

Tests that name the assumption they protect

I write tests against the class of bug, not just the instance. Two commit titles show the habit:

test(entity-version): fail the day the identity mirror gains a reader
test(session): fail the day the embedded pane waits for a token again

Each test is a tripwire: it passes today and goes red the day someone changes the assumption it protects, so the change has to be made on purpose.
