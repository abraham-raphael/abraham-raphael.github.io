Case study · Security, access control

Authorise on the role that is active, not the role a user holds

In September 2026 I audited how the services on our platform make authorisation decisions. Four of them were checking the wrong thing. None of them was failing loudly.

Scope
Every service on a multi-service platform that shares one identity provider
Found
Three defects, present in four services
Outcome
All four fixed, with tests that fail if the defects return

How roles work on the platform

A signed-in user's token describes their roles in four parts:

PartMeaning
Held rolesEvery role the user has been given. Most are dormant at any moment.
Ambient rolesAlways on.
Assumed roleA step-up the user switches on for about 30 minutes, with an expiry time.
Effective rolesAmbient plus assumed: what the user is acting as right now.

The rule is simple: authorise on effective roles, never on held roles. Holding an admin role you have not switched on should get you nothing.

The three defects

1. The join

Some services turned the role list into one string, such as "Employee, Super Admin", and compared the whole string with the role they wanted. That two-role shape is exactly what a real company administrator carries, and it matched nothing.

2. The spelling

Configuration said super_admin; the identity provider sends Super Admin. A normaliser that only removed spaces still missed, because the underscore survived. One file even spelled the same role two different ways in two branches, so one of those branches could never run.

3. Held versus active

A dormant admin role was honoured as if it were switched on. This is the one that is a security issue: elevation should require the user to step up.

Why nobody noticed

The defects failed closed. A two-person approval gate on one product worked perfectly in demo mode and refused every real approver in production. That is never a security hole, but it is a feature that does not work, and nothing logged an error. A check that only ever says no looks exactly like a check doing its job.

The fix

One service on the platform already did this correctly, and more strictly than the specification: it rebuilt effective roles from their parts and re-checked the step-up's expiry. That matters because a token outlives the 30-minute window it may have been minted in. I copied the service that was right, not the document. Two rules now apply everywhere:

  • One spelling per role. Role names are compared after removing spaces, underscores and hyphens and lowering the case, so Super Admin, super_admin and super-admin are the same role.
  • A step-up counts only while its window is open. No expiry, an unreadable expiry, or one in the past: no elevation.

Every check now normalises role names the same way and asks only about effective roles. Each defect has a test that turns red if it comes back.

What I took from it

  • Fail closed, but fail visibly. A denial that should never happen deserves a log line.
  • Copy the implementation that works, even when it disagrees with the document.
  • When you fix a rule, find every other place that answers the same question. The same mistake was in four services.
